## Нотатки ментора — Лекція 1

### 1. Основна ідея лекції

Системний промпт — це не просто текст, який ми один раз написали для LLM.

Це **артефакт системи**, який має:

* власника;
* правила зміни;
* ревʼю;
* версію;
* changelog;
* перевірки;
* критерії готовності до релізу;
* періодичний аудит.

Тобто ми поводимося із системним промптом приблизно так само, як із кодом або конфігурацією.

**Головна думка для студента:**

> Якщо зміна системного промпту може змінити поведінку AI-системи, ця зміна повинна бути керованою та відтворюваною.

---

### 2. Що студент робить на практиці

Студент не просто читає шаблон `Prompt Governance Policy`, а **заповнює його для конкретної AI-системи**.

Він має визначити:

1. хто власник вимоги;
2. хто ревʼює зміни;
3. які частини промпту за що відповідають;
4. що записується в changelog;
5. що є доказом необхідності зміни;
6. які перевірки повинні з'явитися;
7. коли зміна вважається готовою до релізу;
8. що заборонено робити;
9. як контролюється версія промпту;
10. коли проводиться аудит.

Тобто результат лекції — не «я знаю, що таке system prompt», а:

> **Я можу описати процес керування змінами системного промпту для своєї AI-системи.**

---

### 3. Важливий принцип: зміна повинна мати доказ

Особливо звернути увагу студентів на два поля:

* **тип дефекту, який закриває**
* **чим доведено**

Погана зміна:

> «Зробимо промпт більш конкретним».

Це суб'єктивна пропозиція.

Інженерна зміна:

> «У 4 з 20 тестових сценаріїв модель використовує інструмент без перевірки параметра X. Додаємо правило Y. Перевірка Z відтворює дефект на старій версії та проходить на новій».

Тобто ланцюжок:

**дефект → причина/гіпотеза → зміна промпту → перевірка → доказ**

Це один із ключових моментів лекції.

# 4. Практична реалізація

Конкретний технічний приклад.

### Крок 1. Еталонний промпт

У репозиторії зберігаємо версію системного промпту.

Наприклад:

```text
prompts/
├── system_prompt.md
└── old_versions/
    ├── v1.0.md
    ├── v1.1.md
    └── v1.2.md
```

Або ще простіше:

```text
prompts/system.md
```

і версіонування робимо через Git.
Це дозволяє оформити зміну системного промпту як звичайний Pull Request (PR). 

У PR ми пояснюємо:
* що змінилося;
* чому ми це змінюємо;
* на підставі яких метрик / тестових результатів прийнято рішення;
* який очікуваний результат має дати зміна;
* як ми перевіримо, що очікуваний результат отримано.

Таким чином PR — це не просто «змінив текст промпту», а документоване інженерне рішення, яке можна переглянути, обговорити та перевірити.

Приклад:

```sh
PR: Improve refund eligibility rule

Що:
Змінено правило перевірки терміну повернення.

Чому:
У 4/20 тестових сценаріїв модель дозволяла refund
для транзакцій за межами дозволеного періоду.

Evidence:
Domain correctness: 80% → 100%
4 дефекти відтворюються на старій версії.

Очікуваний результат:
Domain correctness = 100%
Жоден із 20 regression cases не повинен погіршитися.

Перевірка:
Golden dataset + regression tests.
```


---

### Крок 2. Промпт, який реально пішов у модель

Важливо розрізняти:

**prompt у репозиторії**

і

**prompt, який реально отримала модель**.

Бо коли промт – просто поле в системі\ базі данних є спокуса змінити його "на льоту"

Наприклад:

```text
Repository prompt
        ↓
application
        ↓
system prompt + variables + policies
        ↓
LLM request
```

Тому в логах бажано мати хоча б:

```json
{
  "prompt_version": "1.3",
  "model": "model-name",
  "request_id": "12345"
}
```

Тоді ми можемо відповісти на питання:

> Який саме prompt і яка модель породили цю відповідь?

# 5. Перевірка фактичного prompt

Вага текстових змін може бути недооцінена або переоцінена.

Приклад, одна зміна:

```text
Do not refund orders older than 30 days.
```

на:

```text
Do not refund orders older than 60 days.
```

може мати дуже маленький текстовий diff, але **величезний функціональний вплив**.

І навпаки, зміна великого explanatory-блоку на 20% може взагалі не змінити поведінку.

Тому слід робити дві різні перевірки:

### A. Text diff

Контролюємо, що фактичний prompt відповідає очікуваному.

Наприклад:

```python
expected_prompt = load_from_repo()
actual_prompt = get_prompt_from_request()

assert actual_prompt == expected_prompt
```

Або якщо допустимі runtime variables:

```python
assert normalize(actual_prompt) == normalize(expected_prompt)
```

Це перевіряє **цілісність/відповідність prompt artifact**.

---

### B. Behavioral diff

Беремо набір контрольних сценаріїв:

```text
test_cases/
├── refund_30_days.json
├── refund_60_days.json
├── unauthorized_action.json
└── tool_validation.json
```

І проганяємо:

```text
old prompt
    ↓
test dataset
    ↓
outputs

new prompt
    ↓
same test dataset
    ↓
outputs
```

Після цього порівнюємо поведінку.

Саме тут з'являється справжня QA-частина.

---

# 6. Дуже важливий практичний принцип

**Текстовий diff показує, що змінився prompt. Behavioral diff показує, що змінилася поведінка системи.**

І вони відповідають на різні питання.

| Перевірка        | Що перевіряє                                   |
| ---------------- | ---------------------------------------------- |
| Git diff         | Що змінилося в тексті                          |
| Prompt equality  | Який prompt реально використовується           |
| Golden tests     | Як система поводиться на контрольних сценаріях |
| Metrics          | Наскільки змінилася якість                     |
| Regression tests | Чи не зламали стару поведінку                  |

---

# 7. Щодо порогу 5%

Слід сказати, що правило `diff > 5% = fail` НЕ є універсальним.

Ми використовуємо 5% як **навчальний приклад або policy конкретної команди**:

> Якщо текст prompt змінився більше ніж на 5%, потрібен додатковий review.

Але це не означає:

> більше 5% = prompt поганий.

І не означає:

> менше 5% = prompt безпечний.

З тестів поведінки видний контраст:

```text
5% text diff
        ↓
не означає
        ↓
5% behavior change
```

Фактично навіть **одне слово** може змінити поведінку моделі.

---

# 8. Мінімальний pipeline для першої лекції

```text
Зміна system prompt
        ↓
Git diff
        ↓
Review
        ↓
Prompt version
        ↓
Golden test dataset
        ↓
Old prompt ──────┐
                 ├──→ compare results
New prompt ──────┘
        ↓
Metrics / assertions
        ↓
Regression check
        ↓
Release
```

І ключова вимога:

> **Хоча б одна перевірка повинна падати на старій версії та проходити на новій.**

Бо інакше тест може просто перевіряти, що система «і зараз працює», але не доводити, що **саме зміна prompt щось виправила**.

## 9. Що студент повинен уміти після лекції

Я б сформулював це як checklist ментора.

Після лекції студент повинен вміти:

* [ ] пояснити, чому system prompt є керованим артефактом;
* [ ] визначити власника вимоги;
* [ ] визначити reviewer'ів;
* [ ] створити prompt version;
* [ ] вести changelog;
* [ ] зафіксувати дефект, який виправляється;
* [ ] описати evidence;
* [ ] отримати diff між версіями;
* [ ] відтворити дефект на старій версії;
* [ ] перевірити нову версію;
* [ ] виконати regression check;
* [ ] відрізнити **text diff** від **behavioral diff**;
* [ ] зрозуміти, чому `prompt + model` — це фактична тестована конфігурація.

### І головне

Після першої лекції студент повинен вийти не з думкою:

> «Я знаю, що таке system prompt».

А з навичкою:

> **«Я можу поставити system prompt під контроль як інженерний артефакт і довести, що його зміна справді щось виправила».**
