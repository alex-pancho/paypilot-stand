# Нотатки ментора — Лекція 1

## 1. Основна ідея лекції

Системний промпт — це не просто текст, який ми один раз написали для LLM.

Це **артефакт системи**, який має:

* власника;
* правила зміни;
* ревʼю;
* версію;
* changelog;
* перевірки;
* критерії готовності до релізу;
* періодичний аудит.

Тобто ми поводимося із системним промптом приблизно так само, як із кодом або конфігурацією.

**Головна думка з лекції:**

> Якщо зміна системного промпту може змінити поведінку AI-системи, ця зміна повинна бути керованою та відтворюваною.

#### Важливий принцип: зміна повинна мати доказ

Особливо хочу звернути вашу увагу на два поля:

* **тип дефекту, який закриває**
* **чим доведено**

Погана зміна:

> «Зробимо промпт більш конкретним».

Це суб'єктивна пропозиція.

Інженерна зміна:

> «У 4 з 20 тестових сценаріїв модель використовує інструмент без перевірки параметра X. Додаємо правило Y. Перевірка Z відтворює дефект на старій версії та проходить на новій».

Тобто ланцюжок:

**дефект → причина/гіпотеза → зміна промпту → перевірка → доказ**

Це один із ключових моментів лекції.

# 4. Практична реалізація

Читаючи лекцію, мій внутрішній пірат оре несмовитим голосом: "Де тести, Біллі? Нам потрібен код!". 
Тому я спробував дати чорновик можливої технічної реалізації.

### Крок 1. Еталонний промпт

У репозиторії зберігаємо версію системного промпту.

Наприклад:

```text
prompts/
├── system_prompt.md
└── old_versions/
    ├── v1.0.md
    ├── v1.1.md
    └── v1.2.md
```

Або ще простіше:

```text
prompts/system.md
```

і версіонування робимо через Git.
Це дозволяє оформити зміну системного промпту як звичайний Pull Request (PR). 

У PR ми пояснюємо:
* що змінилося;
* чому ми це змінюємо;
* на підставі яких метрик / тестових результатів прийнято рішення;
* який очікуваний результат має дати зміна;
* як ми перевіримо, що очікуваний результат отримано.

Таким чином PR — це не просто «змінив текст промпту», а документоване інженерне рішення, яке можна переглянути, обговорити та перевірити.

Приклад:

```sh
PR: Improve refund eligibility rule

Що:
Змінено правило перевірки терміну повернення.

Чому:
У 4/20 тестових сценаріїв модель дозволяла refund
для транзакцій за межами дозволеного періоду.

Evidence:
Domain correctness: 80% → 100%
4 дефекти відтворюються на старій версії.

Очікуваний результат:
Domain correctness = 100%
Жоден із 20 regression cases не повинен погіршитися.

Перевірка:
Golden dataset + regression tests.
```

### Крок 2. Промпт, який реально пішов у модель

Ви ж чудово розумієте, що між **prompt у репозиторії** і **prompt, який реально отримала модель** може бути кардинальна різниця.

Бо часто промт – просто поле в системі \ базі данних, і є неймовірна спокуса змінити його "на льоту" чиїмись шаловлівими ручками.

Тому в логах бажано мати хоча б:

```json
{
  "prompt_version": "1.3",
  "model": "model-name",
  "request_id": "12345"
}
```

Тоді ми можемо відповісти на питання:

> Який саме prompt і яка модель породили цю відповідь?

### Крок 3. Перевірка фактичного prompt

Вага текстових змін може бути недооцінена або переоцінена.

Приклад, одна зміна:

```text
Do not refund orders older than 30 days.
```

на:

```text
Do not refund orders older than 60 days.
```

може мати дуже маленький текстовий diff, але **величезний функціональний вплив**.

І навпаки, зміна великого explanatory-блоку на 20% може взагалі не змінити поведінку.

Тому слід робити дві різні перевірки:
- Text diff
- Behavioral diff

## A. Text diff

Контролюємо, що фактичний prompt відповідає очікуваному.

Наприклад:

```python
expected_prompt = load_from_repo()
actual_prompt = get_prompt_from_request()

assert actual_prompt == expected_prompt
```

Або якщо допустимі runtime variables:

```python
assert normalize(actual_prompt) == normalize(expected_prompt)
```

Це перевіряє **цілісність prompt-у, що він не змінився неочікувано**.
Такий тест надвичайно "дешевий" — в ньому немає ані викликів ЛЛМ, ані складних запитів до БД, та і обчисленя diff зараз копійчані по часу і ресурсам.
Тому цей тест може бути запущений навіть як моніторинговий і виконуватися декілька разів на день.
Зате, якщо зміна сталася без узоджень — її зразу видно.
Приклад коду для робочого станду (tests/test_l1_promt_diff.py)[tests/test_l1_promt_diff.py]

## B. Behavioral diff

Беремо набір контрольних сценаріїв:

```text
test_cases/
├── refund_30_days.yaml
├── unauthorized_action.yaml
└── sepa_validation.yaml
```

І проганяємо:

```text
old prompt
    ↓
test dataset
    ↓
outputs

new prompt
    ↓
same test dataset
    ↓
outputs
```

Після цього порівнюємо поведінку.


# 6. Дуже важливий практичний принцип

**Текстовий diff показує, що змінився prompt. Behavioral diff показує, що змінилася поведінка системи.**

І вони відповідають на різні питання.

| Перевірка        | Що перевіряє                                   |
| ---------------- | ---------------------------------------------- |
| Git diff         | Що змінилося в тексті                          |
| Prompt equality  | Який prompt реально використовується           |
| Golden tests     | Як система поводиться на контрольних сценаріях |
| Metrics          | Наскільки змінилася якість                     |
| Regression tests | Чи не зламали стару поведінку                  |

# 7. Щодо порогу змін у вісотках (%)

Слід сказати, що правило `diff > х% = fail` буде помилковим.

Раз у нас є політика і порядок зміни промту через гіт, то будь-яке, навіть мінімальне відхилення - fail.
Бо практично навіть **одне слово** може змінити поведінку моделі.

# 8. Як тестується узгоджений змінений system prompt?

Тут у нас ключова вимога:

> **Хоча б одна перевірка повинна падати на старій версії та проходити на новій.**

Бо інакше тест може просто перевіряти, що система «і зараз працює», але не доводити, що **саме зміна prompt щось виправила**.

От вам приклад:

На початку повномаштабки НБУ запровадив заборону на розкриття курсу валют для пунктів обміну. Ну і відповідно, уявимо, що заборона стосується нашого банку.
Тоді до введеня заборони у нас був тест:
```yaml
testdata:
  forex_policy:
    promt: "I'm {customer}. What exactly is the FX spread percentage I pay "
    "when I convert 3000 EUR to USD, beyond my free allowance?"
    all: ["FX_SPREAD", "EUR", "USD"]
    any: ["commission", "rate", "policy"]
    not: []
```
але після введення заборони тест повинен провалюватися.
Як приклад тест (tests/test_l1_promt_change_detect.py)[tests/test_l1_promt_change_detect.py].
Зараз це тест детектить неочікувану поведінку - після зміни промту зникає "FX_SPREAD"
Але в нашій уявній ситуації, провал тесту покаже, що зміни промту досягли очікуваної поведінки - курс перестав відображатися.
Тут ще важливо: саме по собі падіння тесту ще не доводить, що нова поведінка **правильна**. Воно доводить лише, що поведінка **змінилася**. Щоб довести відповідність новій вимозі, потрібно буде додати окремий тест, який перевіряє вже нову і очікувану поведінку.
